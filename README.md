## nftables Firewall:

This is an nftables firewall build for NixOS.

The firewall is designed to default-deny traffic unless it is explicitly permitted. It allows required Mullvad VPN traffic, SSH from local network, and traffic for libvirt virtual machines.

As of writing this documentation (07/10/2026), I have been using and modifying this firewall since around May 2026. The original intention was to create a kill switch, but the configuration has since evolved out of necessity.

## Objectives:

This firewall is designed to:

* Default deny all inbound and outbound traffic unless explicitly permitted.
* Allow established and related connections.
* Allow VPN traffic (mullvad).
* Allow SSH traffic from local network.
* Allow and route all virtual machine traffic through the VPN, and deny VM traffic outside that.

## Architecture

The firewall contains two nftables tables:

* `inet filter` - handles filtering of incoming, forwarding and outgoing packets.
* `ip nat` - handles NAT for virtual machine traffic.

## Firewall Design

### Default-deny

The `input`, `forward` and `output` chains all use the default `drop` policy, meaning all traffic is denied unless a rule explicitly allows it. An exception had to be made for port 51820 to allow the WireGuard handshake, but that means that port 51820 currently is unrestricted.

```nft
chain input {
    type filter hook input priority 0;
    policy drop;
}
```

```nft
chain forward {
    type filter hook forward priority 0;
    policy drop;
}
```

```nft
chain output {
    type filter hook output priority 0;
    policy drop;
}
```

This makes a good baseline to explicitly allow what we want.

## Input Filtering

The input chain controls what traffic enters the host.

### Loopback

```nft
iifname "lo" accept
```

Traffic arriving through the loopback interface (lo) is allowed. This is so local processes can communicate with each other.

### Established and Related Connections

```nft
ct state established,related accept
```

Traffic belonging to already-established connections, or connections related to an existing connection, is accepted.

This allows return traffic for connections that have already been permitted without needing to create individual rules for every response packet.

### Mullvad VPN

```nft
iifname "mullvad" accept
```

Traffic arriving through the mullvad interface is permitted.

### Libvirt DHCP

```nft
iifname "virbr0" udp dport 67 accept
```

UDP traffic destined for DHCP port 67 arriving through the libvirt bridge is allowed.

This is required for the virtual machines connected to `virbr0` to obtain network configuration.

### Libvirt DNS

```nft
iifname "virbr0" udp dport 53 accept
iifname "virbr0" tcp dport 53 accept
```

DNS queries from the libvirt network are permitted over both UDP and TCP locally.

### SSH from LAN

```nft
ip saddr 192.168.1.0/24 tcp dport 22 accept
```

SSH connections originating from the local 192.168.1.0/24 network are explicitly permitted. Connections from outside this network are not explicitly permitted and are therefore dropped by the default policy.

## Forwarding

The forward chain controls traffic passing through the host rather than traffic destined for the host itself.

### VM → Mullvad VPN

```nft
iifname "virbr0" oifname "mullvad" accept
```

Traffic originating from the libvirt network is permitted to leave through the mullvad VPN interface.

This is the main path for VM internet access.

### Mullvad VPN → VM

```nft
iifname "mullvad" oifname "virbr0" ct state established,related accept
```

Return traffic from the VPN to the virtual machines is permitted when it belongs to an established or related connection.

Because the forward chain has a default-drop policy, other forwarding paths are denied.

---

## Output Filtering

The output chain controls traffic generated by the host.

### Loopback

```nft
oifname "lo" accept
```

Allows locally generated loopback traffic.

### Established and Related Connections

```nft
ct state established,related accept
```

Allows return traffic belonging to existing connections.

### Mullvad VPN

```nft
oifname "mullvad" accept
```

Allows host traffic to leave through the mullvad VPN interface.

### SSH to LAN

```nft
ip daddr 192.168.1.0/24 tcp dport 22 accept
```

Allows the host to establish SSH connections to machines on the local network.

### Libvirt DHCP

```nft
oifname "virbr0" udp sport 67 udp dport 68 accept
```

Allows DHCP responses to be sent from the host's DHCP service to virtual machines.

### WireGuard Handshake

```nft
oifname { "eno1", "wlp9s0" } udp dport 51820 accept
```

Allows WireGuard handshake traffic to leave through the physical network interfaces.

This traffic must be allowed through the physical network interface because the WireGuard tunnel needs to establish a connection before the `mullvad` interface can be used.

---

## NAT

A separate `ip nat` table performs masquerading for virtual machine traffic.

```nft
ip saddr 192.168.122.0/24 oifname "mullvad" masquerade
```

Traffic originating from the libvirt network is masqueraded when leaving through mullvad.

This allows multiple virtual machines using the private `192.168.122.0/24` network to share the host's VPN connection.

## Testing

I have tested all features extensively by using this configuration daily and testing it with online tools.

* Forcing traffic through the VPN tunnel.
Tested using https://mullvad.net/en/check which checks VPN, DNS and WebRTC leaks.

* VPN disconnect & kill switch.
Verified that traffic cannot leave through any other interfaces while the VPN is disconnected or when the mullvad interface is dropped.

* Libvirt through NAT using VPN.
Verified that VM traffic is forced through the mullvad VPN tunnel and cannot use the physical network directly.

* SSH from LAN.
Verified that I can use SSH from my LAN.

## Future Improvements

* Review the permitted traffic and tighten the rules where possible, including restricting WireGuard handshake traffic to known Mullvad endpoint IP addresses.

* Currently, UDP port 51820 is unrestricted by destination IP. This is intentional, as it allows WireGuard to establish a handshake and switch between VPN servers without requiring manual changes to the firewall rules. However, it also allows outbound UDP traffic to any destination on that port. One possible improvement would be to restrict this traffic to known Mullvad server IP addresses, although those addresses may change over time and require the rules to be updated.
